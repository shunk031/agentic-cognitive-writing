# LLM による長文ライティング品質評価のデータセット・ベンチマーク調査

## 0. 要約

この調査の問いは、Flower & Hayes の Cognitive Process Theory of Writing に基づく writing agent を、既存の long-form writing benchmark でどう公平に評価できるかである。計画中の実験設計は、利用者の最終確認前の planned design として、次の 6 arms を比較する: (1) single-shot generation、(2) linear Pre-Write/Write/Re-Write pipeline、(3) STORM-style linear pipeline を retrieval なしで再実装した arm、(4) planner/translator/reviewer sub-agent を monitor が制御する theory-based agent、(5) ablation A: no goal network、(6) ablation B: fixed process order。全 arms は equal-tool/equal-information policy に従い、同一 input context を受け取り、web access/retrieval は使わない。

調査方法は、まず arXiv、ACL Anthology、Hugging Face、project site などの paper/official source を読み、次に GitHub の README だけでなく data definition、judge prompt、evaluation script、license file を確認し、矛盾する情報は VERIFIED と HYPOTHESIS に分けて記録する、という順序にした。ここでいう **VERIFIED** は、この調査で直接 URL を開いて内容を確認した主張である。**HYPOTHESIS** は、実験設計上の推定、または直接確認できなかったが候補として残す情報である。

結論として、主実験の primary benchmarks は **WritingBench、HelloBench、DoLoMiTes の 3 つに固定する**のが最も堅い。WritingBench は一般的な書く能力、HelloBench は長文生成能力、DoLoMiTes は構造化された専門的 writing を測れる。LongBench-Write は primary から外し、benchmark prompt files の license/provenance が確認できた後にだけ、optional supplementary length-control axis として使う。PERSUADE 2.0 と ICLE++ は主ベンチではなく、argumentative writing prompt と human-quality anchor の供給源として使う。これにより、最終成果物の品質だけでなく、計画・翻訳・レビュー・モニタリングというプロセス差が出やすい条件を作れる。

実験設計上の意味は明確である。agent の内部 trace は judge に見せず、6 arms すべてが同じ prompt/context から最終 output だけを出す設定にすれば、product quality は公平に比較できる。一方で、Flower & Hayes 型 agent の主張を支えるには、別枠で planning trace、revision behavior、goal reference、process transition を測る必要がある。そのため product-level benchmark と process-level analysis を分け、judge は rubric pointwise と balanced pairwise を併用する。

したがって主評価には、単一モデル API だけでなく agentic system が同じ prompt に対して最終成果物を返せること、長文生成を実際に要求すること、judge rubric が明示されていること、再現可能な prompt/data と license が確認できることが必要である。

推奨構成は次の通り。

- **主ベンチ 1: WritingBench**。1,000 real-world writing queries、6 domains、100 subdomains、query-specific 5 criteria で、一般目的の「書く能力」に最も近い。agent は同じ query に最終回答だけを返せばよいので公平に接続できる。VERIFIED: paper/repo/data/eval prompt を確認。Paper: https://arxiv.org/abs/2503.05244 / Repo: https://github.com/X-PLUG/WritingBench / Data: https://github.com/X-PLUG/WritingBench/blob/main/benchmark_query/benchmark_all.jsonl / Eval prompt: https://github.com/X-PLUG/WritingBench/blob/main/prompt.py
- **主ベンチ 2: HelloBench**。647 samples、5 tasks、38 subcategories、long text generation 専用で、checklist-wise LLM judge と human annotation/regression を持つ。planner/translator/reviewer 型 agent の効果が出やすい。VERIFIED: paper/repo/judge code を確認。Paper: https://arxiv.org/abs/2409.16191 / Repo: https://github.com/Quehry/HelloBench / Judge code: https://github.com/Quehry/HelloBench/blob/main/llm_judge.py
- **主ベンチ 3: DoLoMiTes**。専門家の methodical writing tasks と expert-edited references に強く、研究計画・報告・設計文書に近い。DoLoMiTes VERIFIED: paper/repo/data/license を確認。Paper: https://arxiv.org/abs/2405.05938 / Repo: https://github.com/google-deepmind/dolomites / Data: https://dolomites-benchmark.s3.us-west-2.amazonaws.com/dolomites_tasks_anon.jsonl / Examples: https://dolomites-benchmark.s3.us-west-2.amazonaws.com/dolomites_examples.zip
- **prompt-source / human-anchor** は PERSUADE 2.0 と ICLE++ を優先する。PERSUADE 2.0 は 25,000+ argumentative essays と holistic/discourse effectiveness scores を持つため、argumentative prompt と人間品質分布の anchor に使いやすい。ICLE++ は persuasive essays に holistic and trait-specific scores を付けた ASAP 外の generalization anchor になる。PERSUADE VERIFIED: Repo/Paper metadata/license を確認。Repo: https://github.com/scrosseye/persuade_corpus_2.0 / Paper/record: https://zenodo.org/records/8221504 / ICLE++ VERIFIED: ACL/repo/license を確認。Paper: https://aclanthology.org/2024.naacl-long.468/ / Repo: https://github.com/samlee946/ICLE-PlusPlus

推奨 judge setup は、**rubric pointwise + pairwise の二重化**である。一次スコアは task-specific rubric/checklist の 1-5 or 1-10 pointwise、最終比較は 6 arms の条件ペアごとの pairwise preference とする。6 arms では 15 pairs/prompt になり、A/B と B/A の両順序を走らせるため 30 pairwise judgments/prompt/judge が必要である。human validation は主ベンチから層化抽出して 180-240 comparisons 程度にし、15 arm-pairs が各 12-16 回は人手確認されるように割り付ける。各 comparison は 3 annotators、Krippendorff's alpha または Fleiss' kappa と judge-human agreement を報告する。

## 3. LLM-as-judge methodology for writing quality

### 3.1 Biases and mitigations

- VERIFIED: MT-Bench/Chatbot Arena paper identifies position bias, verbosity bias, self-enhancement bias, and limited reasoning ability; GPT-4 matched human preferences above 80% agreement in their studied setup, with 80 MT-Bench questions, 3K expert votes, and 30K arena conversations released. Sources: https://arxiv.org/abs/2306.05685 / https://github.com/lm-sys/FastChat/tree/main/fastchat/llm_judge
- VERIFIED: FastChat judge prompts explicitly instruct the judge to avoid position bias, length influence, and assistant-name bias; implementation supports single grading, pairwise-baseline, and pairwise-all modes. Sources: https://github.com/lm-sys/FastChat/blob/main/fastchat/llm_judge/data/judge_prompts.jsonl / https://github.com/lm-sys/FastChat/blob/main/fastchat/llm_judge/gen_judgment.py
- VERIFIED: G-Eval uses task definition + criteria + CoT-generated evaluation steps + form-filling scores, and reports stronger Spearman correlation with human judgments on summarization than prior metrics. It also warns that LLM evaluators can prefer LLM-generated summaries over human-written summaries. Sources: https://arxiv.org/abs/2303.16634 / https://github.com/nlpyang/geval
- VERIFIED: Prometheus 2 supports both direct assessment and pairwise ranking with user-defined rubrics; the paper/repo emphasize open evaluator transparency and report human/proprietary-judge correlation/agreement. Sources: https://arxiv.org/abs/2405.01535 / https://github.com/prometheus-eval/prometheus-eval
- VERIFIED: LongJudgeBench specifically studies long-form judge reliability; it reports task-specific length sensitivity, that rubric/reference modes help on some datasets and hurt on others, and no single judge is universally reliable. Sources: https://arxiv.org/abs/2606.01629 / https://github.com/cjj826/LongJudgeBench

### 3.2 Recommended judge design for our experiment

Codex recommends the following protocol.

1. **Product-quality pointwise score**: for each output, ask two judge families to score independently on 5 dimensions: Instruction Fulfillment, Organization/Global Coherence, Content Adequacy/Depth, Style/Voice/Audience Fit, Factuality/Constraint Fidelity. Use a 1-5 anchored rubric with JSON output and a short evidence quote/rationale.
2. **Pairwise preference score**: for every prompt, compare the 6 arms in a balanced tournament: 15 unordered arm pairs, A/B and B/A orders, therefore 30 pairwise judgments per prompt per judge. Count ties explicitly. This directly controls position bias and reduces scale-compression issues.
3. **Blinding and presentation controls**: hide condition names from judges and human annotators; use neutral labels such as Output A/B or randomized anonymous IDs. Human annotation UI should randomize output order per comparison and hide benchmark/source names when feasible.
4. **Judge/generator separation**: pin exact judge model versions, prompts, decoding parameters, and seeds. Prefer judge models that are not used as generators; if overlap is unavoidable, run an explicit self-preference test by comparing judge-family outputs against non-overlapping outputs under swapped order.
5. **Length control**: record word/token length; report quality both raw and length-stratified. Add length-matched sensitivity analysis where possible and otherwise include output length as a covariate in regression/Bradley-Terry analysis. Do not include length compliance in the same score as literary/content quality unless the benchmark requires it.
6. **Multi-judge aggregation**: use one strong proprietary judge and one open evaluator or smaller verifier. If budgets allow, add a third judge specialized in writing. Aggregate by z-scored dimension average for pointwise and majority/Bradley-Terry for pairwise.
7. **Human validation**: sample 180-240 pairwise comparisons, stratified by benchmark, arm pair, prompt length, output length gap, and close-vs-clear automatic decisions. With 6 arms, this gives 12-16 human-checked examples for each of the 15 arm pairs. Use 3 annotators per comparison. Report human-human agreement, judge-human agreement, and disagreement analysis. This mirrors the 200-pair DoLoMiTes validation scale and MT-Bench's controlled preference protocol without making human annotation the whole experiment.

## 4. Process-level evaluation precedents

Product-only evaluation misses the central claim of a Flower & Hayes-inspired writing agent. The process trace should therefore be evaluated separately from final product quality.

- VERIFIED: IteraTeR is a large-scale, multi-domain, edit-intention annotated corpus of iteratively revised text; it models revision depths, granularities, and edit intentions, and connects edit intentions to writing quality. Sources: https://aclanthology.org/2022.acl-long.250/ / https://github.com/vipulraheja/IteraTeR / https://github.com/vipulraheja/IteraTeR/blob/main/dataset/README.md
- VERIFIED: IteraTeR-HUMAN document-level split includes 481 train, 27 dev, 51 test documents; sentence-level split includes 3,254 train, 400 dev, 364 test; edit actions include add/delete/replace, spans, majority intent, raw intents from 3 annotators. Source: https://github.com/vipulraheja/IteraTeR/blob/main/dataset/README.md
- VERIFIED: ArgRewrite V.2 was built around student-driven revision sessions for argumentative writing, including interaction with an NLP-based revision assistant. Sources: https://github.com/omidkashefi/ArgRewrite / https://doi.org/10.1007/s10579-021-09567-z
- VERIFIED: Revision Quality Prediction frames argumentative revision quality as success/failure dependent on argument context and uses chain-of-thought generated argument contexts for prediction. Sources: https://aclanthology.org/2023.bea-1.24/ / https://github.com/ZhexiongLiu/Revision-Quality-Prediction

Process fairness policy: all 6 arms receive identical input context, tools, output budget, and no web access. The STORM-style arm is therefore a **linear outline/write/revise pipeline inspired by STORM**, not the full retrieval-based STORM system; retrieval, evidence gathering, and citation trace metrics are N/A by design for every arm.

For the 6-arm experiment, process metrics should be:

- **Planning trace**: number and specificity of goals, whether goals cover audience/purpose/content/organization/style, and whether goals are referenced later.
- **Translation trace**: whether drafts are grounded in plan items, whether sections are expanded in coherent order, whether constraints are preserved.
- **Review trace**: number/type of detected issues, revision intent taxonomy mapped to clarity/fluency/coherence/style/meaning-change, and whether fixes improve final rubric scores.
- **Monitor trace**: process order entropy, transitions between planning/translating/reviewing, and whether transitions respond to detected problems rather than fixed sequence.
- **STORM-style arm trace**: outline structure, simulated question/answer or perspective decomposition if used, section allocation, and linear handoff completeness. Retrieval/evidence/citation traces are explicitly N/A under the no-retrieval policy.
- **Ablation-specific checks**: no-goal-network should show fewer explicit goal references; fixed-process-order should show lower adaptive transitions even if final quality is similar.

## 5. Final recommendation

### 5.1 Primary benchmark shortlist

1. **WritingBench**
   - Why: best match for general-purpose writing, broad domains, explicit criteria, current leaderboard/evaluation scripts.
   - Fairness: high; all 6 arms can submit final outputs to the same query set under the equal-context/no-retrieval policy.
   - Risk: some prompts include long materials and domain-specific details; ensure identical input context and output budget.

2. **HelloBench**
   - Why: explicitly targets long text generation and has checklist-wise evaluation plus human annotation/regression tooling.
   - Fairness: high; use the same wrapped prompt and fixed generation budget for all systems.
   - Risk: contains multiple task types; report subtask breakdown and avoid overclaiming "writing" from summarization/chat alone.

3. **DoLoMiTes**
   - Why: best match for structured expert writing, planning, and methodical output.
   - Fairness: high; all 6 arms get the same task description and input example, with retrieval disabled.
   - Risk: split-size conflict must be resolved by recomputing the released archive before final reporting.

**Optional supplementary axis: LongBench-Write**

- Use only for length-control analysis after clearing benchmark prompt-file license/provenance.
- Do not count it as a primary benchmark.

### 5.2 Prompt-source / human-anchor datasets

1. **PERSUADE 2.0**
   - Use 15 prompts as argumentative writing prompt templates.
   - Use holistic score distribution to calibrate human quality anchors.
   - Do not train on student essays for this paper unless license/consent scope is reviewed.

2. **ICLE++**
   - Use as external validation of essay-trait rubrics and cross-prompt generalization.
   - Good for argumentative/persuasive writing traits, weaker for creative/general writing.

### 5.3 Judge setup

- Run pointwise rubric with JSON schema on all outputs.
- Run pairwise A/B and B/A on all 15 condition pairs for the primary subset: 30 judgments per prompt per judge.
- Blind condition labels and randomize presentation order for human annotators.
- Use at least two judges: a strong frontier judge for main numbers and Prometheus-style open evaluator for reproducibility/sensitivity. Pin exact model versions, prompts, decoding parameters, and seeds.
- Avoid judge/generator overlap where possible; otherwise run a self-preference diagnostic.
- Report per-dimension score, aggregate score, pairwise win rate, length-normalized or covariate-adjusted score, and judge agreement.
- Human validation: 180-240 pairwise comparisons, 3 annotators each, stratified by benchmark, arm pair, automatic-decision margin, and output-length gap. Report Krippendorff's alpha/Fleiss' kappa, raw agreement, and judge-human agreement.
