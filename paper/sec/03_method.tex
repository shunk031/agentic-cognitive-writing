Figure~\ref{fig:agentic-cogwriter} shows the architecture of \condAgenticCogWriter. The input is a writing task together with any task-specific context and output constraints; the output is a completed document. The system runs inside a coding-agent harness and uses a shared workspace to persist the document and intermediate writing state across agent calls. A host agent acts as the \texttt{Monitor}. Rather than following a pre-written sequence of writing stages, the \texttt{Monitor} repeatedly inspects the current workspace, decides what kind of writing work is needed next, and delegates that work to a specialized agent.

\subsection{Persistent writing state}
\label{sec:method-control-state}

At each decision point, the shared workspace contains three records. The \emph{draft} is the document produced so far. The \emph{goal network} is an explicit hierarchical record of current writing goals. The \emph{process history} records previous writing-process choices and changes to those goals. We denote these records immediately before decision $t$ as
\begin{equation}
S_t=(D_t,G_t,H_t),
\end{equation}
where $D_t$, $G_t$, and $H_t$ are the draft, goal network, and process history, respectively. The original writing instruction and its constraints remain fixed task context available to the agents throughout the run.

The goal network operationalizes one idea from Flower and Hayes~\cite{flower1981cognitive}: writing is guided by goals that can develop as composition proceeds. In our implementation, goals can be created, made more specific, or replaced. We call replacement of an existing goal \emph{goal regeneration}. These events are logged so that changes to the explicit goal representation can be analyzed later. The goal network is therefore an observable system record, not a claim about latent cognitive state.

\subsection{Agentic writing loop}
\label{sec:method-writing-processes}

The \texttt{Monitor} can choose among three writing activities. \texttt{Planning} develops or reorganizes writing goals and structure; \texttt{Translating} turns the current goals into prose in the shared draft; and \texttt{Reviewing} evaluates the draft against the task and current goals and proposes revisions when needed. We write the runtime choice as
\begin{equation}
a_t \in \{\mathrm{Planning},\mathrm{Translating},\mathrm{Reviewing}\},
\qquad
a_t=\pi_{\mathrm{monitor}}(S_t),
\end{equation}
where $\pi_{\mathrm{monitor}}$ is the prompted decision made by the host agent rather than a separately trained policy.

Once an activity is selected, the corresponding role agent executes it: the \texttt{Planner} performs \texttt{Planning}, the \texttt{Translator} performs \texttt{Translating}, and the \texttt{Reviewer} performs \texttt{Reviewing}. Each role agent reads the shared workspace and writes its updates back before returning control to the \texttt{Monitor}. Review may also produce a proposal to change the goal network; the \texttt{Monitor} accepts or rejects that proposal and records the decision. The loop continues from the updated state until the \texttt{Monitor} decides after review that no further writing action is needed.

This runtime choice is the main organizational difference from a fixed writing pipeline. The system may plan again after drafting, draft again after review, or revisit planning when review reveals a structural problem. The specialized role contexts are an implementation choice of the full system; the experiments vary both the process-order policy and several execution details to determine which parts of the architecture are associated with the observed performance.
