Figure~\ref{fig:agentic-cogwriter} motivates a different answer to the question of what a writing controller should do next. Rather than choosing the next section, passage, or task, Agentic CogWriter maintains an explicit writing state and chooses which writing process to execute next. We now define that process action space and the state on which the choice is conditioned.

\subsection{Writing state}
\label{sec:method-control-state}

At writing step $t$, the control state is
%
\begin{equation}
S_t=(D_t,G_t,H_t),
\end{equation}
%
where $D_t$ is the current document, $G_t$ is the writer-goal network, and $H_t$ is the history of process and goal events. The assignment and its constraints remain fixed task context rather than part of the evolving state.

The goal network contains content, process, and evaluation goals organized hierarchically. A local goal can be developed under a parent goal, and resolving it returns attention to the parent. The implementation records goal creation, development, and regeneration so that changes to $G_t$ are observable in the trace. This representation operationalizes the writer-generated goals in the cognitive process theory~\cite{flower1981cognitive}; it is an external control state, not a claim about a model's latent cognition.

\subsection{Process action space}
\label{sec:method-writing-processes}

The controller chooses among three actions,
%
\begin{equation}
a_t \in
\{\mathrm{Planning},\mathrm{Translating},\mathrm{Reviewing}\},
\end{equation}
%
using
%
\begin{equation}
a_t=\pi_{\mathrm{monitor}}(S_t).
\end{equation}
%
In the evaluated system, $\pi_{\mathrm{monitor}}$ is the prompted decision of the host agent over the current state and open uncertainty, not a separately trained policy.

Each action is executed by a corresponding role agent. The \texttt{Planner} runs \texttt{Planning} to create or refine goals and organize their pursuit. The \texttt{Translator} runs \texttt{Translating} to realize active goals as prose and primarily changes the document. The \texttt{Reviewer} runs \texttt{Reviewing} to evaluate the draft against active goals and can request further planning or translation. A process execution produces an updated state before returning control to the \texttt{Monitor}.

\subsection{Control loop}
\label{sec:method-monitor}

The loop permits any next process rather than imposing a stage sequence. For example, translation can expose a planning problem, and review can return control to planning or translation. Review can also trigger goal regeneration when the draft changes the writing problem. The executed process, its state changes, and any goal events are appended to $H_t$ before the next decision. Generation terminates when \texttt{Reviewing} returns no next process.

This architecture separates three design commitments that can be tested independently: maintaining explicit evolving goals, selecting process order dynamically, and executing the writing processes as distinct roles. Section~\ref{sec:baselines} defines the interventions used to test those commitments.
