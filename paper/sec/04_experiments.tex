\subsection{Research questions}
\label{sec:research-questions}

We ask two questions. \textbf{RQ1} asks whether choosing among writing processes improves long-form writing relative to a single call, fixed writing stages, and adaptive task planning. \textbf{RQ2} asks which architectural commitments account for any improvement: explicit writer goals, adaptive process ordering, or separation of the writing processes. We use process traces to interpret RQ2 rather than treating trace behavior as a separate product claim.

\subsection{Conditions}
\label{sec:baselines}

We compare seven organizations of long-form writing under the same generator and harness. Table~\ref{tab:experimental-conditions} summarizes what each condition selects next during generation and the intervention dimensions.

The first three conditions provide increasingly structured baselines. \condSinglePass\ generates the document in one call. \condStaged\ executes a fixed \texttt{Pre-Write}$\rightarrow$\texttt{Write}$\rightarrow$\texttt{Re-Write} sequence. \condTaskPlanning\ follows the adaptive task-planning pattern of WriteHERE~\cite{xiong2025beyond}, selecting dependency-satisfied nodes from an evolving task graph. These are controlled re-implementations on our generator and harness rather than executions of the published systems.

The remaining conditions intervene on the process-level architecture. \condFull\ maintains the goal network, lets the \texttt{Monitor} choose the next writing process, and delegates each process to its corresponding role agent. \condNoGoals\ removes the explicit goal network while retaining adaptive process choice and role delegation. \condFixedOrder\ retains the state and role agents but replaces the \texttt{Monitor}'s choice with a fixed \texttt{Planning}$\rightarrow$\texttt{Translating}$\rightarrow$\texttt{Reviewing} cycle. \condSingleWriter\ removes the delegated role structure and writes recursively in one context at paragraph granularity. Because \condSingleWriter\ changes both role separation and recursion granularity, it is a diagnostic ablation rather than a clean estimate of delegation.

\subsection{Benchmarks and prompts}
\label{sec:benchmarks}

We use WritingBench~\cite{wu2026writingbench}, HelloBench~\cite{que2024hellobench}, and DoLoMiTes~\cite{malaviya2025dolomites}. WritingBench covers general-purpose writing with task-specific criteria, HelloBench contains long-text generation tasks across several genres, and DoLoMiTes contains structured expert-writing tasks such as plans, reports, and design documents. Their source pools contain 1,000, 647, and 820 prompts, respectively.

We select the 100 prompts per benchmark that request the longest outputs, for 300 prompts total. The ranking combines prompt word count with the largest explicitly requested output length; we exclude pilot identifiers and prompts requesting more than 6,000 words in either component. This hard slice is intended to expose architectural differences in demanding long-form settings. The conclusions therefore concern this slice rather than the full benchmark distributions. All conditions receive the same prompt and benchmark information, and external retrieval is disabled.

\subsection{Controlled implementation}
\label{sec:implementation}

We hold the generator, task input, available information, tool availability, and final-output contract fixed across conditions. Every prompt--condition pair is generated in three independent replications. The generator is \modelGen; runtime details are reported in Appendix~\ref{app:runtime}.

The implementation uses the host platforms' documented skills and subagent mechanisms~\cite{anthropicAgentSkills,anthropicSubagents,openaiBuildSkills,openaiSubagents,googleAntigravitySkills,googleAntigravitySubagents}. For \condFull, the host agent acts as the \texttt{Monitor}, while \texttt{Planner}, \texttt{Translator}, and \texttt{Reviewer} subagents operate over a shared working directory containing the draft, goal network, and process history. The same harness records process switches, goal events, completed outputs, delegated invocations, token accounting, and timing. All conditions return the complete document through the same output channel.

\subsection{Evaluation}
\label{sec:evaluation}

\paragraph{Primary outcome.}
Our confirmatory outcome is pairwise preference between two outputs for the same prompt. The judge is \modelJudge, which shares the generator's model family; primary claims are therefore conditional on same-family judging. Each pair is judged in both presentation orders. If both orders select the same winner, that winner is retained; any disagreement becomes a tie. Prompts lacking a completed output from either side are excluded.

The locked confirmatory family contains eight contrasts: \condFull\ versus \condSinglePass, \condStaged, \condTaskPlanning, \condNoGoals, and \condFixedOrder; and \condSingleWriter\ versus \condSinglePass, \condFull, and \condNoGoals. Across three benchmarks this yields 24 benchmark-by-contrast cells. We use exact two-sided sign tests on wins and losses and control family-wise error with Holm's procedure~\cite{dixonmood1946,holm1979}. We report pooled prompt-collapsed win rates across the three replications with 95\% Wilson intervals~\cite{wilson1927}; replicate-specific cells show stability across generation runs.

\paragraph{Secondary outcomes and robustness.}
Benchmark-native and pointwise scores are secondary diagnostics from the first replication. We test output-length sensitivity using 5\% and 10\% matching bands. We test inference-compute sensitivity using cumulative output-plus-reasoning tokens and symmetric compute-ratio bands; because realized compute is an outcome of execution, these analyses are descriptive robustness checks rather than causal adjustment. Finally, \modelCross\ provides a cross-family pairwise check on selected contrasts. Its results are descriptive rather than a second confirmatory family.

\paragraph{Process traces.}
To interpret RQ2, we analyze observable process and goal events rather than latent reasoning. We count process transitions, goal creation, development and regeneration, returns after \texttt{Reviewing}, and delegated invocations. Task-graph events from \condTaskPlanning\ are kept separate from writing-process events because the two conditions make different kinds of next-step decisions.
