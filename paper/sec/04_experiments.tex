We design the experiments to answer three progressively narrower questions: whether process-level organization improves document quality, which parts of \condAgenticCogWriter\ account for any advantage, and how the resulting writing loop behaves in practice. The study contains seven pre-specified systems plus one post-hoc execution check, all compared on the same task inputs and under a common generation contract.

\subsection{Systems compared}
\label{sec:baselines}

\paragraph{Alternative writing architectures.}
We compare \condAgenticCogWriter\ with three ways of organizing long-form generation. The one-shot baseline (\condSinglePass) asks the model to produce the complete document in one call. The fixed-stage baseline (\condStaged) executes \texttt{Pre-Write}$\rightarrow$\texttt{Write}$\rightarrow$\texttt{Re-Write}, following the common pattern of separating planning, drafting, and revision into a prescribed workflow~\citep{yang2022re3,wan2025cognitive}. The adaptive task-planning baseline (\condTaskPlanning) follows a WriteHERE-style task graph~\citep{xiong2025beyond}: it recursively decomposes the assignment and selects among dependency-satisfied task nodes. Thus, the three alternatives respectively advance the whole document, a fixed writing stage, or an adaptive task node, whereas \condAgenticCogWriter\ advances a writing process.

\paragraph{Ablations of \condAgenticCogWriter.}
We next modify one architectural choice at a time while leaving the rest of the process loop intact. \condNoGoals\ removes the explicit goal network but retains adaptive process selection and the specialized agents. \condFixedOrder\ keeps the shared draft, goal network, process history, and specialists but replaces the \texttt{Monitor}'s adaptive decision with the repeated \texttt{Planning}$\rightarrow$\texttt{Translating}$\rightarrow$\texttt{Reviewing} cycle. These ablations test whether explicit goal bookkeeping and adaptive process order are individually necessary for the full system's performance.

\paragraph{Execution variants.}
We also probe whether the way writing processes are executed can explain the result. \condSingleWriter\ retains the goal network and process-level loop but performs planning, drafting, and reviewing in one writer context without role-agent delegation; it also limits each \texttt{Translating} step to one paragraph before the next process decision. Because those changes are bundled, this condition is diagnostic rather than a clean ablation. After observing the main results, we added \condSingleContext\ as a narrower exploratory check: it preserves the full process loop and shared state but executes each selected process in the \texttt{Monitor}'s context rather than in a separate role-agent context. The run also differs in gateway entry point and transport, so we use it only to constrain, rather than establish, a role-context explanation. \subsection{Benchmarks and prompts}
\label{sec:benchmarks}

To evaluate whether the architecture transfers across different forms of long-form writing, we use three complementary benchmarks. WritingBench~\citep{wu2026writingbench} covers broad real-world writing requests and supplies task-specific evaluation criteria. HelloBench~\citep{que2024hellobench} contains long-text tasks across categories such as summarization, open-ended generation, and text completion, with checklist-based evaluation. DoLoMiTes~\citep{malaviya2025dolomites} focuses on methodical expert writing in which the output must follow explicit objectives, procedures, inputs, and constraints. Together, the three benchmarks probe general instruction following, sustained long-form generation, and structured expert-document production rather than a single writing genre.

Because the experiment targets architecture rather than basic short-form fluency, we evaluate a pre-committed set of demanding long-form prompts. For each benchmark, the selector excludes pilot prompts and ranks the remaining examples by an operational difficulty score combining input word count and the largest requested output length; the top 100 eligible prompts form the \texttt{hard100} slice, for 300 prompts total. This definition deliberately emphasizes context handling and sustained generation, but it is not an independent semantic difficulty measure. The sample count was fixed before scoring rather than chosen after observing an effect size, so our statistical claims rely on prompt-level exact tests and uncertainty intervals and are limited to this pre-committed slice. Appendix~\ref{app:prompts} gives the deterministic selection rule, provenance, and generation contract.

\subsection{Generation setup}
\label{sec:implementation}

All generations use \modelGen\ with medium reasoning effort inside the same Codex-style coding-agent harness. Holding the generator fixed across conditions makes the comparison about writing architecture rather than base-model capability. \condAgenticCogWriter\ is packaged as a skill whose \texttt{Monitor} can invoke \texttt{Planner}, \texttt{Translator}, and \texttt{Reviewer} through the harness's subagent mechanism; the comparison systems use the same harness and task-level information policy. The implementation follows the platforms' documented skill and subagent abstractions~\citep{anthropicAgentSkills,anthropicSubagents,openaiBuildSkills,openaiSubagents,googleAntigravitySkills,googleAntigravitySubagents}.

Each prompt--system pair is generated in three independent replications. The harness records completed outputs and, where applicable, process switches, goal events, delegated invocations, token accounting, and timing. Network access, web search, and external retrieval are disabled for every condition so that architecture cannot change the information available to the writer. Appendix~\ref{app:runtime} reports the complete runtime settings. The repository records the chosen generator and reasoning effort but no separate rationale for selecting that exact model setting; we therefore avoid attributing results to a claimed model-selection principle that was not pre-specified.

\subsection{Evaluation}
\label{sec:evaluation}

\paragraph{Pointwise evaluation.}
We first score each completed document independently to measure document quality without reference to another system's output. WritingBench uses its task-specific criteria and HelloBench uses its benchmark checklists as benchmark-native evaluation; DoLoMiTes does not provide a corresponding native score in our setup. We additionally apply a common pointwise rubric covering instruction fulfillment, organization and coherence, content adequacy and depth, style and audience fit, and factual or constraint fidelity. The evaluator prompts and benchmark-specific procedures are reproduced in Appendix~\ref{app:prompts}.

The reported pointwise composite puts heterogeneous rubric dimensions on a common scale. For each benchmark and judge, we standardize each criterion to a z-score and then average across criteria, so zero represents the corresponding reference mean and negative values mean below-average standardized performance, not ``negative writing quality.'' Benchmark-native scores remain on their original scales and are reported separately. These independent scores come from the initial replication and are descriptive rather than replicated inferential outcomes.\footnote{All reported systems are our implementations under the shared generator and harness. Their scores should therefore not be compared numerically with published full-benchmark leaderboard values for the original systems.}

\paragraph{Pairwise evaluation.}
Independent rubric scores can hide small but consistent differences between two systems, and a ten-prompt pilot showed saturation on the generic pointwise scale. We therefore also ask a judge to directly compare two responses written for the same prompt. To reduce presentation-position effects, every comparison is judged twice, once as A-versus-B and once with the responses swapped to B-versus-A. We retain a prompt-level winner only when both orders identify the same semantic winner; any disagreement, including winner versus tie, is recorded as a tie. Prompts lacking a completed output from either system are excluded from that contrast.

The pre-specified analysis plan called for a judge from a different model family than the generator, whereas the completed pre-specified contrasts use \modelJudge. We report that deviation transparently and evaluate the same selected contrasts with \modelCross\ as a descriptive cross-family robustness check. The pairwise rubric asks about the same document-quality dimensions as the generic pointwise evaluator rather than introducing a separate notion of quality.

\paragraph{Pre-specified statistical testing.}
To avoid choosing favorable contrasts or tests after seeing the results, we fixed the inferential family before scoring. The eight contrasts compare \condAgenticCogWriter\ with \condSinglePass, \condStaged, \condTaskPlanning, \condNoGoals, and \condFixedOrder, and compare \condSingleWriter\ with \condSinglePass, \condAgenticCogWriter, and \condNoGoals. Within each benchmark, each contrast is tested separately in each replication with an exact two-sided sign test over non-tied prompt-level wins and losses~\citep{dixonmood1946}; Holm correction~\citep{holm1979} is then applied jointly to the resulting pre-specified cells for that benchmark. We never pool prompts across replications for confirmatory inference. Main-text tables report descriptive replicate means, while Appendix~\ref{app:pairwise-detail} reports replication-level Wilson intervals~\citep{wilson1927} and the multiplicity-adjusted decisions.

\paragraph{Robustness and behavioral analysis.}
Architecture can change output length and inference compute, and aggregate scores alone do not reveal how an adaptive writing agent actually uses its control loop. We therefore pair the main evaluation with two complementary analyses. First, we check whether the pairwise direction persists within pre-specified output-length bands and under a tight compute match; because both variables are consequences of execution, these are descriptive sensitivity analyses rather than causal adjustments. Second, we analyze observable traces of process transitions, goal creation and refinement, goal replacement, and delegated invocations. We also compare outcomes from runs that complete one planning--drafting--reviewing cycle with outcomes from runs that take another process path; this trace-defined comparison is observational, not randomized.
